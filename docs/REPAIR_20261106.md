Every Kubernetes arm keeps a watch of its serving pods from before its window to after it (`tools/bench_integrity.py`,
`docs/REPAIR_20261029.md`), and an arm whose watch has a gap is refused, because a gap could hide a pod's start or its
Ready transition. This note changes one case of that rule: a gap is now admitted when a fresh read of the pods proves that
nothing happened in it. Every other gap is refused as before.

## 1. What was refused, from the runs' own files

All 32,525 pod watch receipts on the branch `raw` were read on 6 November. 32,399 are complete. Of the 126 that are not,
36 stopped on one answer from the API server, `410 Expired, too old resource version`:

| Where | Arms refused | Which arms |
|---|---|---|
| The Azure steady set on omni-v21 (run 40940616527) | 30, in 26 repetitions | 16 native, 14 Omni-Compass |
| Kind, Koordinator's rigs on omni-v25 (runs 41806648201, 41810789445, 42173251769) | 4 | Omni-Compass |
| Kind, two older runs (41221965342, 41319675248) | 2 | Omni-Compass |

The Azure set ended in failure on 3 November with 27 of its 100 repetitions refused (`docs/RUN_LEDGER.md`). This fault
refused 26 of them. The 27th (repetition 70) stopped before its window opened, and its files hold no reason. The three
Koordinator runs are why no three runs of Koordinator's four ways stand on omni-v25.

The remaining 90 incomplete receipts are a different fault: requests to the API server failed. 14 fell under the first
form of the rule, which refused a single failed request (repaired in `docs/AUDIT_2026-10-30.md`). 76 fell under today's
five-in-a-row rule. All 76 were Omni-Compass arms on the seven-organism grid, 74 at 500 copies and 2 at 100, and their
errors read `TLS handshake timeout` and `http2: client connection lost`. The API server stopped answering on a runner
loaded with hundreds of copies. That rule is unchanged here (section 4).

## 2. The cause

Kubernetes serves a watch from its watch cache, a window of recent changes. A watch resumes at the last version it was
given, and the cache replays every change after that version. If the cache no longer holds the version, the API server
answers 410 Expired. In every one of the 36 receipts, the watch's last version was 1 to 321 versions older than the
first version the cache held. That means the cache had started again from a fresh read at a later version. On kind's one
API server this happens when its own watch of etcd breaks. On a managed cloud, another API server may answer the
request. Every Kubernetes client that keeps a watch (client-go's informers) answers a 410 by listing again. Ours refused
the arm, because a new list could hide what happened between the last version and the list.

## 3. The repair

On a 410, the collector lists the serving pods again and reads that list against what its watch already holds
(`tools/bench_integrity.py`, `bridge`). The gap is **empty**, and the watch resumes at the list's version, only when all
of these hold:

- the list is not older than the last version the watch delivered;
- every pod listed is one the watch already holds, at the exact resourceVersion the watch last delivered for it, so
  nothing wrote the pod since;
- every pod the watch holds is listed, so none was deleted;
- every version involved is a number. The comparison is the one the API server's own cache makes (etcd's revision), and
  a version that is not a number proves nothing.

A pod written, created or deleted in the gap fails the receipt, as every gap did before. So does more than five
expired histories in a row. Each gap is written into the arm's receipt (`pod_watch_receipt.json`, `gaps`): its two
versions, the pods listed, the pods written or gone, and whether it was empty. When a report reads the arm,
`validate` checks the gaps again and refuses any that was not empty. The stream (`pod_watch.json`) keeps only the
watch's own events. Nothing from the list is copied into it, because an empty gap adds no event.

Under this rule nothing is estimated. An admitted arm's pod times are Kubernetes' own timestamps from an unbroken
record of every change to every serving pod. A gap is admitted only when that record is provably whole.

`tests/test_bench_integrity.py` covers the case from run 42173251769, the 410 said by the client, a write, a deletion and
a new pod in the gap, a list older than the watch, versions that are not numbers, any other API error, expired histories
again and again, and the report's second check. Eight of the new tests fail on the tool before this repair, and all 25
pass on it.

## 4. What this does not do

- The 36 refused arms stay refused. Their watches took no list at the time, so no proof exists for them. No table
  changes, and the Azure steady set on omni-v21 is still read in no table.
- The engine is unchanged. `tools/bench_integrity.py` is the rig's evidence tool, outside the engine's fingerprint.
  `python3 tools/omni_version.py` reads omni-v25, digest cf56fc0a7b707452, 65 files. The rig marker
  (`tools/confirm_abc.py`, `rig`) is unchanged.
- The client-failure rule is unchanged: five failed requests in a row fail the receipt. A resumed watch loses nothing,
  so a longer wait would keep the record whole. But an API server that does not answer for a minute also stalls the
  governor and Kubernetes' own controllers, and an arm run on a starved control plane measures the test machine. The 76
  grid arms are listed as refused. Their cause, the API server unanswered on a runner at 100 and 500 copies with
  Omni-Compass on top, is open. The governor's own reads on a shared machine are the suspected part
  (`docs/LOSS_CAUSES_2026-11-05.md`, section 2), not yet measured.
- On kind, all six arms refused for an expired history were Omni-Compass arms. Whether the governor's reads at the 10 s
  beat make the API server's cache start again more often has not been measured.

Koordinator's four ways run again whole on the repaired tool (`scripts/reruns.txt`, the block added on 6 November), and
their table is written from the new three runs.
